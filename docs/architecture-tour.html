五个工具，
一根管子

这是一个让 AI 模型能读写 GitHub issue 的小程序。它自己不会上网——它只会做一件事： 在你的电脑上敲 gh 这个命令行工具，然后把结果翻译回去。 整个系统就是这一根管子，以及围着它写的一大堆规矩。

四件是读，一件是写。所有工具的头两个参数都一样：仓库归谁、叫什么。

为什么说是「一根管子」

五个工具各写各的，但要出门只有一道门。这是整个设计里最要紧的一条规矩。

坏掉的时候说什么

这个系统不按「错在哪」分类，按「你现在该做什么」分类。 因为读的人是模型，模型需要的是下一步动作，不是病因。一共只有五种回答。

RETRY等一下再试一次。比如撞到限流、网络不通。
CHECK_BEFORE_RETRY先去查一下写进去没有，再决定要不要重来。只有那个写工具会给出这个。
FIX_REQUEST你问的东西不对。号码不存在、仓库名写错了、这个仓库关掉了 issue。
ASK_OPERATOR模型自己解决不了，得找人。没装 gh、没登录、登录了但没权限。
UNKNOWN看不懂 gh 在抱怨什么。原话原样奉还，不猜。

中间那张 10 行的对照表只认识 gh 说过的几种话，而且每一行都得附上一句 真的见过的错误原文当证据。没见过的措辞不许写进去—— 猜一句进去，就等于让系统对着一个它没验证过的情况，自信地给出一个可能是错的建议。

哪里确实不对劲

按「会不会咬到人」排，不按好不好看排。多数问题项目自己已经记下来了。

会咬人

贴一条评论要打两通电话，中间没保险

先问「这条 issue 的内部编号是多少」，再拿编号去贴。两步之间如果 issue 被关掉、被锁上， 失败发生在第二步。更糟的是：第二步超时的时候，程序不知道评论到底贴进去没有。

项目的处理：不重试，改成告诉模型「先去查一下有没有」。这是那个第二种回答存在的唯一理由。
会咬人

看不懂的错误，就变成一句「我不认识」

对照表只有 10 行。任何 gh 没被记录过的抱怨都会掉到 UNKNOWN， 模型拿到一句原始英文报错，得自己猜怎么办。表能认多少，取决于有人真的撞见过多少。

这是设计上的取舍，不是遗漏：宁可说不知道，也不给一个自信的错答案。
别扭

那根管子里写死了一个工具的名字

管子的说明文档写着「所有工具共用同一套规矩，不含任何针对单个工具的代码」—— 然后紧接着就有一句写死的提示语，里面点名了 list_issue_comments。 改名字不会有任何编译错误，只会让那句话悄悄变成谎话。

项目自己承认了：第二个写工具出现时就是该改的时候，现在还不到。
别扭

五个工具，十个一模一样的参数

owner 和 repo 在每个工具上重复一遍，21 个参数里占了 10 个。 另外，GraphQL 的查询语句是手写在这个程序里的——GitHub 改了 schema，这里就得跟着改。

别扭

大仓库基本翻不动

每次最多 100 条，排序改不了，而且砍掉的永远是最旧的那些。 读一条长讨论串是「每 100 条一次调用」，而且只能从最新的一头往回翻。

够不着

有一种失败，这个项目量不出来

issue 被「锁定」时会发生什么，表里没有对应的行。今天实测过：锁对仓库主人根本不生效， 而没权限的身份在锁生效之前就已经被拒了。要撞到这一格，需要第二个 GitHub 账号。

从「还没量」改写成了「够不着」——这不是待办事项，是一条边界。

一句话总结

五个很薄的工具，一根很厚的管子，外加一本厚得离谱的说明书。

薄和厚都是故意的：工具薄，所以加第六个几乎不花钱；管子厚，所以坏掉的方式只需要想明白一次。 说明书厚，是因为这个项目有条铁律——凡是没亲眼见过的，不许写进代码里当事实。 代价就是上面那张图：真正干活的代码只占七分之一。
