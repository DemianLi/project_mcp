MCP 的一問一答：Client 問，Server 答

兩個程式隔著一條管子講話。這頁用四張圖講完：誰跟誰講話、管子上傳什麼、Client 裡面怎麼轉、Server 裡面怎麼轉。右邊一欄是備注——每個專有名詞寫著白話意思，還有該去哪一頁學。

MUST不做就不合規 SHOULD可以不做，但要記在案 MAY隨你 常見做法不是規格條文 強度等級出自 RFC 211914

先認角色

誰跟誰講話

你用的 App 叫 Host1。它裡面有一個或多個 Client2，每個 Client 只連一個 Server3。

備注

  1. 1Host 宿主程式——使用者直接在用的 App。裡面放 LLM、管一群 Client，也負責「同意」與授權。去哪學：architecture/index.mdx §Host ↗
  2. 2Client 客戶端連線——Host 裡的一條連線，跟 Server 是 1 對 1。負責協商、收發訊息。去哪學：architecture/index.mdx §Clients ↗
  3. 3Server 服務端——提供 tools／resources／prompts 的程式。可以是本機子進程，也可以是遠端服務。去哪學：server/index.mdx ↗
  4. 4process boundary 行程邊界、隔離——Server 讀不到整段對話，也「看不進」別的 Server。去哪學：architecture/index.mdx §Design Principles 第 3 條 ↗

Client ↔ Server 交互

管子上傳什麼

一條 stdio6 管子，裡面一行一則 JSON-RPC5 訊息。一生分四段：開機、握手、做事、關機。

  • 先握手，再做事。initialize 還沒收到回覆之前，Client 除了 ping 什麼請求都不該送。版本號是日期，不是 1.0 或 2.0。
  • 叫工具只要兩句：tools/list 看菜單，tools/call 點菜。
  • 工具跑失敗，要回 isError: true，模型才看得到、才會改；回 JSON-RPC error 就像這通電話沒打過，模型多半看不到。

管子上真正的一來一回（示意，欄位取自 ToolResults.java）

→ Client {"jsonrpc":"2.0","id":7,"method":"tools/call",
           "params":{"name":"get_issue","arguments":{"owner":"DemianLi","repo":"project_mcp","number":12}}}

← Server {"jsonrpc":"2.0","id":7,"result":{
           "content":[{"type":"text","text":"{\"number\":12,\"title\":\"…\", …}"}]}}   成功：一段 JSON 文字

← Server {"jsonrpc":"2.0","id":7,"result":{
           "content":[{"type":"text","text":"#12 is a pull request, not an issue. …"}],
           "structuredContent":{"remedy":"FIX_REQUEST","message":"…","stderr":""},
           "isError":true}}                                    失敗：還是 result，不是 error

備注

  1. 5JSON-RPC 2.0 訊息格式——request 帶 id、一定要回；notification 不帶 id、不回；回應是 result 或 error 二選一。去哪學：jsonrpc.org/specification ↗
  2. 6stdio transport 標準輸入輸出傳輸——Client 把 Server 當子進程啟動，stdin 送、stdout 回，一行一則，訊息裡不能有換行。去哪學：basic/transports.mdx §stdio ↗
  3. 7initialize · protocolVersion 初始化、版本協商——第一次互動 MUST 是它。Server 會那一版就回同一版，不會就回自己支援的版本。去哪學：basic/lifecycle.mdx §Initialization ↗
  4. 8capabilities 能力宣告——兩邊先說自己會什麼（tools、sampling…），之後只准用談妥的。去哪學：basic/lifecycle.mdx §Capability Negotiation ↗
  5. 9tools/list · inputSchema 工具清單、參數表——每個工具附一張 JSON Schema，模型靠它知道要餵什麼參數。去哪學：server/tools.mdx ↗ · JSON Schema 入門 ↗
  6. 10tools/call · CallToolResult · isError 呼叫工具、工具結果——錯誤分兩種：協議錯誤走 JSON-RPC error，工具執行錯誤走 isError: true。去哪學：server/tools.mdx §Error Handling ↗
  7. 11notifications/cancelled 取消通知——「那一通我不等了」。收到的一方 SHOULD 停手；請求未知或已完成時 MAY 忽略。去哪學：basic/utilities/cancellation.mdx ↗
  8. 12sampling · elicitation · roots 反向請求——Server 請 Client 幫忙叫模型、問使用者、告知可用資料夾。Client 要先宣告能力才行。去哪學：client/sampling.mdx ↗ · elicitation.mdx ↗ · roots.mdx ↗
  9. 13SIGTERM · SIGKILL 終止訊號——stdio 沒有「再見」訊息：先關 stdin，等不到就 SIGTERM，再等不到就 SIGKILL。去哪學：basic/lifecycle.mdx §Shutdown ↗
  10. 14MUST · SHOULD · MAY 規範強度——這是等級，不是語氣。讀規格先看這個字。去哪學：RFC 2119 ↗

MCP Client 內部資料流

Client 裡面怎麼轉

模型從不直接碰 Server。一個問題會先經過 Host、模型、Client 三站才出門，而且中間有一站是「問人」。

  • 這一段本 repo 沒有程式碼。project_mcp 只是 Server；以上依規格 architecture、lifecycle、server/tools 三頁畫成，標「常見做法」的那一格不是條文。
  • 人可以在中間按「不要」。規格建議：讓人看得到有哪些工具、呼叫當下看得見、敏感操作先確認、參數先給人看。
  • 別太相信 Server 的自我介紹。工具附的 annotations18（例如「我是唯讀的」），Client MUST 當成不可信，除非那個 Server 本身可信。

備注

  1. 15tool use · function calling 工具定義與呼叫——Host 把 tools/list 的結果轉成模型 API 的工具格式；模型回「要叫哪個、參數多少」。MCP 規格不管這段。去哪學：搜尋 function calling、tool use＋你用的模型 API
  2. 16human in the loop 人在迴路中——規格要求 SHOULD 永遠有人能拒絕工具呼叫。去哪學：server/tools.mdx 開頭的 Warning ↗
  3. 17request timeout 請求逾時——每個送出的請求 SHOULD 有逾時；逾時後 SHOULD 送取消通知並停止等待。去哪學：basic/lifecycle.mdx §Timeouts ↗
  4. 18tool annotations 工具提示標註——readOnlyHint、destructiveHint 等。只是提示，不能拿來當權限依據。去哪學：server/tools.mdx §Tool ↗
  5. 19self-correction 模型自我修正——把 isError 的內容交給模型，它才有機會改參數再試。去哪學：server/tools.mdx §Error Handling ↗
  6. 20Client 安全建議 全是 SHOULD——敏感操作要確認、先給人看參數、結果驗過再交模型、有逾時、留稽核紀錄（audit log）。去哪學：server/tools.mdx §Security Considerations ↗

MCP Server 內部資料流

Server 裡面怎麼轉

中間一條直線是任何 MCP Server 都會走的路；右邊寫 project_mcp 怎麼做；左邊是會提早離開的出口。

  • 最容易漏看的是黃色那格。被 schema 擋下的呼叫根本進不到你的程式：它是 isError，但沒有 remedy、也不留 log。偏偏漏參數、型別錯正是模型最常犯的錯。
  • 你的程式裡，失敗只有一個出口。所有會失敗的工作都放進 ToolResults.attempt(…) 裡；丟在外面的失敗會被框架接走，remedy 就不見了。
  • stdout 是給 JSON-RPC 用的。一行 print、一個開機 banner，對方的解析器就壞了。log 一律寫檔。
  • 寫入操作受速率限制。add_issue_comment 限制在每分鐘 80 次、每小時 500 次（GitHub 公開限制），超過時回 isError: true 加 Remedy: RETRY 與 retryAfterSeconds，讀取操作無限制。

備注

  1. 21MCP SDK 協議函式庫——替你做握手、分派、schema 推導。本例是 MCP Java SDK，外面包 Spring AI。去哪學：modelcontextprotocol/java-sdk ↗ · Spring AI MCP Server ↗
  2. 22dispatch · JSON-RPC error code 分派、錯誤碼——依 method 找處理者；找不到工具、格式壞，就回 JSON-RPC error（例如 -32602）。去哪學：jsonrpc.org/specification §5.1 Error object ↗
  3. 23schema validation 參數驗證——框架先拿 inputSchema 驗，在你的方法體之前就擋下。去哪學：design.md#input-validation ↗、docs/mcp-2025-11-25-commercial-primer.html 第 04 條
  4. 24@McpTool 工具註解——Spring AI 把一個 Java 方法變成一個 MCP 工具，參數表自動變成 inputSchema。去哪學：Spring AI MCP Server ↗
  5. 25failure contract · Remedy 失敗契約、補救分類——失敗按「你現在該做什麼」分五類。去哪學：design.md#failure-contract ↗
  6. 26MDC · correlation ID 診斷上下文、關聯編號——把 callId 貼在同一通呼叫的每一行 log 上，事後才串得起來。去哪學：SLF4J manual §MDC ↗
  7. 27ProcessBuilder · pipe draining 起子進程、抽乾管道——stdout 與 stderr 要同時讀，否則緩衝區滿了兩邊互等，形成 deadlock。去哪學：ProcessBuilder (Java 25) ↗
  8. 28ECS 結構化日誌格式——Elastic Common Schema，一套公開的 JSON log 欄位命名，收集器不用翻譯就能讀。去哪學：Elastic ECS ↗
  9. 29stdout purity stdout 純淨——stdio 下 Server MUST NOT 往 stdout 寫任何不是 MCP 訊息的東西；寫 stderr 則 MAY。去哪學：basic/transports.mdx §stdio ↗
