規格修訂版 2025-11-25

一個 MCP Server 要滿足什麼，才敢拿去商用

「商用」不是功能多。是有人把公司的帳號、資料和錢綁在你這支程式上跑， 出事的時候有人要負責。這頁把要求分成兩堆：規格白紙黑字寫的—— 違反了就是不合規，對方有理由拒收；以及規格沒管、但客戶一定會問的。

兩堆混著講，是新手最容易踩的坑。混久了就會講出「規格要求你上 Micrometer」這種話， 在專業場合會被當場糾正。

先認得規格裡的大寫字

MUST沒做就是不合規
MUST NOT做了就是不合規
SHOULD可以不做，但要記在案
MAY隨你

這四個字出自 RFC 2119，是等級，不是語氣。讀規格時先看這個字，再看句子。 另外一個習慣要一開始就養成：講 MCP 一定要帶日期。 這套規格沒有語意化版本號，只有修訂日期（2024-11-05、2025-03-26、2025-06-18、2025-11-25、2026-07-28）。 大家嘴上的「MCP 2.0」指的是 2026-07-28 那一版，跟這頁講的不是同一份文件。

第一部

規格說了算

以下每一條都能在 2025-11-25 的規格文字裡指出出處。違反了，你就是不合規。

01MUST NOT

管子裡只能流 MCP 訊息

stdio 傳輸下，你和 Client 之間只有一條管子。管子裡的每一行都必須是合法的 MCP 訊息。 你隨手一個 print、框架開機打的 banner、一行 log——對方的 JSON-RPC 解析器就從那裡開始壞。

最難的地方：違反這條不會有編譯錯誤，也不會有測試紅燈。只會在別人的機器上壞。

實例 本專案的 application.yml 把 console appender 關成 OFF、banner 關掉、 web-application-type: none——三行設定，唯一的理由就是這一條。改動之前要知道自己在拆什麼。

講給行家聽

  • stdio transport
  • stdout purity「管子要乾淨」
  • protocol pollution
  • newline-delimited JSON-RPC
  • console appender
  • stderr
02MUST

見面第一件事，講好你會哪一版

連上線的第一次互動 MUST 是初始化。Client 說「我想講 2025-11-25」，你會就回同一版； 不會就回你自己支援的版本，讓對方決定要不要繼續。同時你要交代自己有哪些能力（tools、resources、prompts）。

這段多半是 SDK 幫你做完的。你真正該知道的是：你的版本上限是 SDK 給的，不是你決定的。 問「我這支支援到哪一版」，答案在你的相依鏈裡。

而這整段交握在 2026-07-28 被整個拿掉了，改成無狀態。所以「我的 server 支援 MCP」這句話沒有意義。

  • capability declaration

03MUST

每個工具都要交一張合法的表格

inputSchema MUST 是一個合法的 JSON Schema object，不可以是 null。 這是模型唯一知道「這個工具要餵什麼」的來源。工具名字 SHOULD 是 1–128 字、 只用大小寫字母／數字／_／-／.、不含空白、在同一個 server 內唯一。

開發時最常撞到的是這件事：schema 是從你的方法簽章推導出來的。 所以簽章要保持扁平。想把三個參數收成一個值物件，那個物件會直接變成對外 schema 的形狀—— 要收攏概念，在方法體內構造。

如果你宣告了 outputSchema，回傳的 structured 結果 MUST 符合它。 （附帶一提，很多人不知道：一旦 isError 為真，output-schema 驗證會被跳過。）

04兩種機制

錯誤有兩種，分錯了模型就看不到

「你叫的工具根本不存在」「JSON 格式壞了」——這是協議層的錯，走 JSON-RPC error。 它的意思是：這通呼叫沒有發生過。它到不了模型手上。

「工具跑了，但 GitHub 說你沒權限」「網路斷了」「參數超出範圍」——這是執行層的錯。 要包成一個正常的回覆，裡面 isError: true。模型看得到，才有機會自己改。

再往前一步（規格沒要求，但成熟的 server 都這樣做）：錯誤要按 「你現在該做什麼」分類，不要按「哪裡壞了」分類。 模型不需要知道是 401 還是 403，它需要知道的是——重試、先查再重試、改你的請求、去問人。 這份對照表就是你的失敗契約，是一份要維護的公開介面。

還有一條 SHOULD：回傳 structured content 的時候，也該在文字區塊放一份序列化後的 JSON， 給只會讀文字的舊 Client。要偏離可以——但理由和代價要寫在案。

實測補充 · 這條線上有一個框架挖的洞 上面那套讀起來很乾淨，但真的把 server 跑起來、送一個缺必填參數的呼叫進去—— 而這正是模型最常犯的錯——回來的是這個：
{"content":[{"type":"text","text": "Tool (get_issue) input validation failed: … [: 未找到所需屬性“repo”, : 未找到所需屬性“number”]"}], "isError": true}
isError 是對的，但沒有 structuredContent， 所以沒有 remedy。原因是框架先拿 inputSchema 驗了參數，你的方法體根本沒跑—— 失敗還沒走到你寫的那條出口。而且那串訊息跟著機器的語言設定走： 同一個錯誤，換一台 LANG=ja_JP 的機器就是日文。

要帶走的形狀是這個：你的失敗契約只管得到方法體以內。 方法體之前那一關屬於框架，得自己把它接回來——否則模型最常拿到的那個錯誤， 正好是唯一沒有 remedy 的那個。做一個 MCP 之前， 這一格值得你親手送一次壞參數進去看看你的框架回什麼。

05SHOULD

每個送出去的請求都要有逾時

沒有逾時，等於同意別人讓你永遠等下去。規格這條講的是 MCP 請求本身，通常 SDK 有預設值。

但真正會吊死你的那幾段，規格沒管：你叫起來的子進程、你打出去的 HTTP、你查的資料庫。 那些逾時要自己補，而且選 30 秒還是 300 秒，理由要寫下來—— 這是客戶環境不同時第一個要調的旋鈕。

講給行家聽

  • request timeout
  • hung request
  • subprocess timeout
  • timeout policy要文件化
06MUST ×4

安全那一節，是四條並列的 MUST

規格的 Security Considerations 只有四句話。四句都是 MUST，沒有一句是建議。

  • 驗輸入——邊界值、分頁游標、型別。模型送來的東西一律當成不可信。
  • 做權限——誰能做什麼。可以外包給下游（例如交給 CLI 解析出的登入身分），但要知道那代表「一個進程一個身分」。
  • 限流——注意這個陷阱：下游被 GitHub 限流、你把錯誤如實回報，那不算你在限流。那是你被動反映別人的限流。這條是 MUST。
  • 淨化輸出——這道有兩難：模型需要原文，你不能亂轉義；但那代表 issue 內文裡的惡意內容會原樣送到 Client。至少要把「渲染責任在 Client」寫成一句警語。

講給行家聽

  • input validation
  • access control
  • rate limiting / throttling
  • output sanitization
  • prompt injection
  • XSS渲染端的責任
  • defense in depth
第二部

規格沒說，但客戶會問

以下五條你都可以不做，而且完全合規。但只要有人拿它跑正事，這五條會一條一條找上你。

07商用實務

出事的時候，你要查得到

成功的呼叫如果不留任何痕跡，你手上就只有一句「它壞了」。

三件事，成本由低到高：

  • 日誌要機器讀得懂——JSON 格式，不是人寫給人看的句子。這樣才接得上 ELK 或 Datadog。
  • 要有數字——每個工具的呼叫次數、延遲分佈（P50／P95／P99）、失敗率，而且失敗率要能按失敗類別拆開。
  • 要能串起來——每通請求一個編號，從進來到出去都帶著。跨進程邊界時會斷，那也要知道斷在哪。

stdio 有個現實限制：沒有地方掛 /health 或 /metrics，因為根本沒有 HTTP。 這件事跟第 09 條綁在一起。

  • structured logging
  • JSON appender
  • correlation ID
  • distributed tracing
  • Micrometer
  • P50 · P95 · P99
  • SLI / SLO
  • health endpoint
08商用實務

一個進程，就是一個身分

如果認證是外包給下游工具的（例如讓 gh 自己去讀環境變數裡的 token）， 那整個 server 進程只有一把鑰匙，每次呼叫都用同一把。

  • 單租戶：這是優點。少一層自己蓋的認證，就少一層自己會寫錯的東西。
  • 多租戶 SaaS：這是硬牆。A 的登入狀態就是 B 的登入狀態；A 會看到 B 才有權限看的倉庫。

兩條路：每個租戶開一個進程（部署變複雜，但一行程式都不用改）， 或自己蓋認證層（貴，而且是你最不想寫錯的那一層）。

這件事要寫在部署文件裡。寫在 ADR 裡不算數——ADR 是給後來改程式的人看的， 不是給把它裝起來跑的人看的。

講給行家聽

  • tenant isolation
  • multi-tenancy
  • credential isolation
  • blast radius
  • process-per-tenant
  • OAuth 2.1
  • token rotation
09商用實務

傳輸決定你能不能長大

stdio 是一對一、綁在同一台機器上的：Client 把你當子進程叫起來。 沒有反向代理、沒有負載平衡、沒有水平擴充、沒有健康檢查。 內網單機、單租戶完全夠用；SaaS 不行。

好消息是這件事的成本取決於你的分層。如果工具層完全不碰協議—— 工具只管做事、回一個值，協議的事交給上面那層——換成 HTTP 的時候工具一行都不用改。 這是「分層」在真實世界裡最直接的一次回報。

10商用實務

一個大回應就能把你撐死

把下游的輸出整包讀進記憶體（readAllBytes 之類）， 遇到一個大倉庫的清單查詢，回來的 JSON 可能是 MB 級的。沒有上限，就有 OOM。

補法很便宜：輸出大小設一個上限，超過就回一個「太大了」的失敗； 能分頁的工具全部給游標。這條的修復成本低到沒有理由不做。

  • OOM
  • response size cap
  • pagination / cursor
  • backpressure
  • streaming parse
11商用實務

測試要跨過那條線

單元測試證明你的函式算得對，但它證明不了「送出去的那包 JSON 長得對」。 那兩件事之間隔著一整個框架。

失敗契約特別容易在這裡破：寫法一錯，框架會用它自己的預設路徑接手， 回去的東西 isError 看起來還是對的——但你精心分好的 remedy 和原始錯誤訊息整包不見了。 這種 bug 只有跨過 wire 的驗收測試抓得到，而且它值得為此存在一支專門的測試。

講給行家聽

  • acceptance test
  • contract test
  • across the wire
  • coverage layer
  • test pyramid

學完之後，跟人講這件事的三個習慣

  1. 永遠帶著日期講。「2025-11-25 的 server/tools.mdx 說……」， 而不是「MCP 規格說……」。這套規格沒有語意化版本，只有修訂日期， 而每一版之間有真正的破壞性變更。
  2. 分清楚「規格要求」和「商用要求」。前者你可以引條文，對方要反駁得拿規格出來； 後者你要講的是風險和成本，引條文反而會被抓包。這頁的兩部就是這條線。
  3. 偏離規格不是罪，不記錄才是。SHOULD 可以不做，MUST 有時也真的做不到—— 但要有一份文件寫下理由和代價。審查的時候，「有意偏離、已記載」和「沒想到」是兩件完全不同的事。
