基準是 2025-11-25 修訂版——這正是本專案相依的 MCP Java SDK 2.0.0 所支援的上限 （ProtocolVersions 常數止於 MCP_2025_11_25）。最新的 2026-07-28 修訂版另見 docs/reviews/commercial-readiness.md。

1現行架構

docs/architecture-tour.html 已經畫過「五個工具、一根管子」那一層。這張圖補的是它上面那一層： wire layer——Spring AI 與 MCP SDK 把 @McpTool 方法翻成 tools/list 與 tools/call 的地方。2025-11-25 的要求幾乎全部落在這一層， 所以清單與圖是同一件事的兩種畫法，不是兩份東西釘在一起。

兩件圖上看得出、但值得講白的事：

  • 本專案在 wire layer 沒有程式碼。2025-11-25 的生命週期要求（initialize 必須是第一次互動、版本協商、initialized 通知）全部由 SDK 履行。這是好事，也是限制—— 規格要求做對不代表這個 repo 做對了什麼，規格版本要往前也不是這個 repo 能決定的。
  • 失敗路徑比成功路徑長。成功是 Tool → GhCli → gh；失敗多繞 classify → GhStderr → Remedy，再擲回 ToolResults.attempt。規格允許把錯誤丟成 JSON-RPC protocol error，本專案刻意不那樣做， 理由見下一節。

22025-11-25 開發注意事項

每一列的規格文字都取自官方 repo 的 docs/specification/2025-11-25/， 已於 2026-09-08 逐條打開核對。✓ 符合　△ 有意偏離／需留意　✗ 缺口　— 不適用

2.1 stdio 傳輸

規格強度本專案
Server MUST NOT write anything to its stdout that is not a valid MCP message MUST NOT ✓ application.yml 把 console appender 設為 OFF、 banner 關掉、web-application-type: none，log 全部導向檔案。 這是整個設定檔存在的唯一理由，改動時要知道自己在拆什麼。
Messages MUST NOT contain embedded newlines（訊息以換行分隔） MUST NOT — 由 SDK 的序列化負責。本專案不自行寫入 stdout。
Server MAY write UTF-8 to stderr for any logging purposes MAY △ 本專案寫檔案而非 stderr——比規格要求更嚴，不是不合規。 規格明說 client SHOULD NOT 把 stderr 當成錯誤徵兆，所以寫 stderr 也是允許的。 值得知道的是：2026-07-28 棄用了 MCP Logging 功能，官方建議的替代路徑正是 stdio 下寫 stderr。
來源：basic/transports.mdx §stdio

2.2 生命週期

規格強度本專案
初始化階段 MUST 是 client 與 server 的第一次互動MUST— SDK 負責
Server MUST 以自己的 capabilities 與 information 回應MUST— SDK 負責；名稱與版本取自 application.yml 的 spring.ai.mcp.server
Server 支援請求的版本則 MUST 回同一版本，否則 MUST 回自己支援的版本MUST— SDK 負責，上限 2025-11-25
實作 SHOULD 為所有送出的請求設逾時，逾時 SHOULD 送取消通知SHOULD— 這條綁的是送出請求的一方。本 Server 在 tools/call 上是接收方，而且完全沒用到 server→client 的請求（sampling／elicitation／roots/list 都沒有），所以這條在本專案裡沒有東西可綁，談的是 Client 的時鐘（SDK 對它能送的那些請求持有 requestTimeout，本 Server 從不送）。GhCli.TIMEOUT_SECONDS = 30 是子行程預算，規格隻字未提——兩個時鐘互不知道對方，見 deploying.md 的 Two clocks
取消通知的接收方 SHOULD 停止處理、釋放資源、不回應；但在請求未知／已完成／不可取消時 MAY 忽略SHOULD△ 忽略，走的是規格明列的 MAY ignore。notifications/cancelled 在整個相依堆疊（mcp-core 2.0.0、spring-ai-mcp 2.0.1…）裡不存在，SDK 走未知通知分支：一行 WARN、不回應、不碰 stdout。代價是那個 gh 會跑到自己的 30 秒為止；實測 20.36 秒後仍寫出一個 id 正確的回應。見 ADR-0016

2.3 Tool 定義

規格強度本專案
Tool 名稱 SHOULD 為 1–128 字元、只用大小寫字母／數字／_／-／.、不含空白、在 server 內唯一 SHOULD ✓ 五個名稱全部通過：list_issues、get_issue、 list_labels、list_issue_comments、add_issue_comment
inputSchema MUST 是合法的 JSON Schema object（不得為 null） MUST ✓ 由 Spring AI 從方法簽章推導。 開發時要記住的約束：Tool 方法簽章必須保持扁平——所以 IssueRef 這類值物件是在方法體內構造的，不能出現在參數列上，否則 schema 會跟著變形。
若提供 outputSchema，Server MUST 讓 structured 結果符合它 MUST — 本專案不宣告 outputSchema，此條不生效。 ToolResults 的註解記著另一件相關事實：一旦 isError 為真， McpAsyncServer 會跳過 output-schema 驗證。
Clients MUST consider tool annotations to be untrusted unless they come from trusted servers MUST ✓ 受詞是 client。本專案讀的是自己宣告的 readOnlyHint，用來命名寫入分區，不是拿遠端宣告當權限依據——不觸犯這條。 要留意的是別讓後人把它當成授權判斷往上疊。
來源：server/tools.mdx L201, L213, L219-224, L340

2.4 錯誤與結果形狀

規格強度本專案
兩種錯誤機制：Protocol Errors（未知 tool、格式錯誤、server 錯誤）走 JSON-RPC error； Tool Execution Errors（API 失敗、輸入驗證、業務邏輯）走結果裡的 isError: true 分類 ✓ ADR-0002 把所有失敗歸到後者。理由寫在 ToolResults 的註解裡：protocol error 代表「這通呼叫沒發生」，永遠到不了模型手上， 而 Remedy 的預期讀者正是模型。「gh 沒裝」仍然是一個跑過、但做不到的 Tool。
回傳 structured content 的 tool SHOULD 同時在 TextContent block 裡放序列化後的 JSON（為了向後相容） SHOULD △ 有意偏離，且已記載 失敗路徑的 content 放的是「一句人話 ＋ 逐字 stderr」，不是 structuredContent 的 JSON 序列化。ADR-0002「The payload」一節寫明了理由： content 是必填欄位，讓只渲染文字的 Client 也一定看得到一句話。 代價要知道：一個想從 text block 反向解析 JSON 來取得 Remedy 的 Client 會落空。
Clients SHOULD 把 tool execution error 交給模型以利自我修正 SHOULD ✓ 這是 client 端要求，但本專案整套 Remedy 設計（按「你現在該做什麼」分類、 而非按「錯在哪」分類）正是為了讓這條 SHOULD 有東西可用
來源：server/tools.mdx §Error Handling、§Structured Content

2.5 安全

規格這一節是四條並列的 MUST，也是本文件唯一找到真正缺口的地方。

Servers MUST本專案
Validate all tool inputs ✓ Limits 夾住 limit、Cursors 驗證游標、 get_issue 擋掉 pull request 號碼
Implement proper access controls △ 外包給 gh 解析出的登入身分。ADR-0009 明確決定不在 Server 端建門禁。 單租戶成立；多租戶不成立（見 commercial-readiness §7.1）
Rate limit tool invocations ✗ 缺口 本專案沒有任何節流。gh 撞到 GitHub 限流時會回 RETRY，但那是下游的限流被動反映，不是這個 Server 自己在限流。 規格這條是 MUST。教材情境無妨，商用要補。

3動手前該知道的三件事

1 · 動 application.yml 之前先讀那三行註解

裡面每一項設定都只為一個目的存在：不讓任何東西寫進 stdout。這是 stdio 傳輸唯一的 MUST NOT，違反了不會有編譯錯誤，也不會有測試紅燈——只會讓 Client 那端的 JSON-RPC 解析莫名其妙壞掉。

2 · Tool 方法簽章要保持扁平

Spring AI 從簽章推導 inputSchema，而規格要求它是合法的 JSON Schema object。 把 IssueRef 這類值物件搬到參數列上會直接改動對外的 schema。想收攏概念，在方法體內構造。

3 · 失敗只有一條出口

所有會失敗的工作都要放進 ToolResults.attempt(...) 的 lambda 裡。 在 lambda 外面 擲出的 ToolFailure 會被 Spring AI 自己的 callback 接走， 回一個 isError: true 但沒有 structuredContent 的結果—— Remedy 與 stderr 就這樣消失，而 isError 看起來還是對的。 這是實測出來的，不是推論；FailureContractAcceptanceTest 就是為了抓這個而存在。
